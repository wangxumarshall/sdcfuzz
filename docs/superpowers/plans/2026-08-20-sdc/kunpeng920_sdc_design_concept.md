# 鲲鹏 920 (TaiShan V110) SDC 高效检测用例生成思路

> **核心命题**：突破现有CPU sdc检测工具覆盖率瓶颈，解决“EDA 仿真覆盖率高，但真实 SDC 检出能力低”的痛点。

> **破局命题**：芯片某一部分之所以“weak”有三类根因——**设计期校验冗余不足、老化/工艺退化、业务负载模型**。前两类与 Bottom-Up（微架构设计、布线布局、电路覆盖率）充分耦合；第三类靠 Top-Down 业务画像。从这三点齐攻，攻克SDC检测难题。

---

## 一、现状与痛点剖析：EDA 覆盖率 vs 功能检出率

当前 ARM CPU 的 SDC 检测用例在电路逻辑单元上的覆盖率存在明显短板：

| 单元 | 覆盖率 | 评级 | 说明 |
|------|--------|------|------|
| **FSU**（浮点与向量） | 80% | 🟢 较好 | 防下限不够，缺乏极致操作数压力 |
| **IEX**（整数单元） | 70% | 🟡 一般 | 缺乏长进位链压测 |
| **IFU**（取指单元） | 66% | 🟡 一般 | 分支预测/BTB 路径覆盖浅 |
| **OoO**（乱序执行） | 56% | 🟠 薄弱 | 均匀指令流填不满 ROB/Issue Queue |
| **LSU**（加载/存储） | 54% | 🟠 薄弱 | 未触发 Store Buffer 前递与跨边界分拆逻辑 |
| **L2C**（L2 Cache） | 40% | 🔴 很弱 | MESI/MOESI 状态机基本未遍历 |
| **MMU**（内存管理） | 20% | 🔴 极弱 | TLB（CAM）/PTW 状态机几乎未覆盖 |

> MMU 仅 20% 并非偶然：MMU 大部分电路是 TLB（一种 CAM 内容寻址存储器）和 Page Table Walker 状态机。常规测试多为顺序访存，TLB 命中率极高，根本走不到 CAM 并发比较器与 PTW 复杂状态机——所以“不给”也部分是因为其主体本就是 TLB buffer 之外的少量逻辑。

### 1.1 痛点根因一：EDA 仿真覆盖 ≠ 真实电路注错，是两种不同原理

这是必须先厘清的常识性误区：**EDA 工具仿真覆盖率**与**真实电路注错验证覆盖率**，原理不同、维度不同。

- **EDA 工具仿真覆盖率**侧重量化**结构覆盖率**：它确实可以把“指令”与“微观布线 / Gate 级连接”对应起来——即能回答“这条指令是否经过了某个 Gate / Wire”，做指令级到门级的回溯。但它的本质是**静态结构点亮**：某个点被走过即算覆盖，不关心走过时的电气状态。
- **真实电路注错 / SDC 压测**要的是**功能检出率**：瞬态错误真正发生时，能否被激发出来并被终态比对捕获。它依赖**动态压力**——电压降（di/dt）、时序裕量恶化、温度梯度——这些是 EDA 静态用例天然缺失的。

两者不应混为一谈：单纯依赖 EDA 静态生成的指令集用例，能把“线点亮”（结构覆盖），但点亮的瞬间没有动态压力，逼不出因成本妥协、工艺退化或特定负载引发的瞬态翻转。

### 1.2 痛点根因二：GATE 覆盖率只能保“下限”，上限要靠激发 transient

单看 GATE（门级）覆盖率，检出能力其实不能很高——它只能保住**下限**（保证常见通路至少被走过一遍、不至于完全盲区）。真正决定 SDC 检出能力上限的，是**能不能把潜伏的瞬态错误（transient）激发出来**。

瞬态错误的特征是“偶发、不可复现、受电气环境调制”：同一条指令、同样的操作数，在电压谷底/时序裕量最薄的那一刻才翻车。所以覆盖率数字漂亮 ≠ 检出能力强。要突破上限，必须从“覆盖到”转向“激发得到”——这正是从指令集空间向操作数/执行上下文空间转移的意义。

## 二、芯片“weak”的三因素分类（破局框架）

要“找到 weak 的地方施加更重的压力”，首先得搞清楚 weak 从何而来。造成芯片某个部分 weak，可归纳为三类因素：

| 因素 | 物理本质 | 检测难度 | 对应破局路径 |
|------|----------|----------|--------------|
| **① 设计期校验冗余不足** | 芯片设计时因成本/面积/功耗妥协，部分逻辑路径没有充足的 ECC/Parity 保护（如 ALU 计算路径、TLB 匹配逻辑、乱序控制状态机） | **难**——缺陷已固化在硅上，只能靠压测逼出 | Bottom-Up：从设计端定位无冗余逻辑，定向施压 |
| **② 老化 / 工艺退化** | HCI（热载流子注入）/ NBTI（负偏置温度不稳定性）等老化机制，或工艺波动，导致电路功能退化——容易造成不受控翻转、短路/断路，时序裕量随时间变薄 | **难**——无现成老化模型，需长周期高压暴露 | Bottom-Up：用极端翻转率/进位链逼出时序违例 |
| **③ 业务负载模型** | 特定业务持续激发特定功能模块，使其长期处于高压：数据库重击 LSU，HPC 重击 FSU，虚拟化重击 CSU/MMU | **相对可控**——可从真实负载画像反推 | Top-Down：抽象业务模型，做压力权重分配 |

**破局命题**：前两类因素（设计冗余、老化）的检测办法，往往需要和 **Bottom-Up 微架构/电路脆弱性分析充分耦合**，以提升 SDC 检出能力；第三类靠 Top-Down 业务画像。**从这三个点齐攻，攻克SDC高效准确检测难题。** 这也是本思路区别于“纯追求电路覆盖率”的根本所在——单纯追求电路覆盖率，不仅有上限，而且不具备业务负载模型，不清楚哪些是 weak module/function。

## 三、核心破局思路：两大范式 + 一个方法论

### 3.1 范式一：指令集空间 ──→ 操作数 / 执行上下文空间

不要仅仅满足于 `add x0, x1, x2` 指令被执行过。`add` 这个指令本身的“指令空间”很小，但它的**操作数空间**极大——`0x0000…` 与 `0xFFFF…`、`0x5555…` 与 `0xAAAA…`、`0xFFFFFFFF…+1`（最长进位链）——同一指令在不同操作数下，点亮的 Gate 状态空间天差地别。把压力从“指令种类覆盖”转移到“操作数变异与组合”，覆盖率空间立即被打开一个数量级。

执行上下文空间**主要是操作数空间**，但不止于此，还包括：
- **操作数的变异与组合**：交替喂入全 0/全 1/交替位/非规格化浮点/极大极小值。
- **数据依赖压力**：构造 RAW / WAR / WAW 依赖链积压，逼满 ROB 与 Issue Queue。
- **乱序执行压力**：长依赖链 + 管线气泡积压后并发唤醒（瞬间极高 di/dt）；分支预测欺骗诱导全管线 Flush，压榨乱序恢复逻辑。
- **跨 cache line 压力**：跨 16B/64B 边界的不对齐访问、Store-to-Load Forwarding 的宽写窄读字节拼接。

### 3.2 范式二：均匀覆盖 ──→ 压力权重覆盖

放弃对所有模块的平均用力。从芯片设计端（Bottom-Up）找出脆弱模块，并结合业务负载（Top-Down）施加**不均匀的极压**：薄弱模块（MMU/L2C/LSU/OoO）配重压，已较好模块（FSU/IEX）配防下限的极端操作数压力。

### 3.3 方法论：DOWN-TOP 与 TOP-DOWN 深度融合

SDC 检测用例设计**必须深度分析底层，不能过度从 TOP-DOWN 分析**，要融合一定甚至大量的 **DOWN-TOP 分析**：

- **DOWN-TOP（自底向上）**：结合 ARM64 微架构设计、**布线布局（floorplan/place&route）**、电路覆盖率——从物理实现层面定位哪些模块/功能/网络最脆弱（高扇出、长组合逻辑路径、无 ECC 保护、易时序违例）。
- **TOP-DOWN（自顶向下）**：业务负载模型——数据库/虚拟化/HPC 各自激发哪些模块。

ARM64 芯片设计师单纯追求电路覆盖率，不仅有上限，而且不具备业务负载模型，不清楚哪些是 weak module/function，仍有进步空间。**只有 DOWN-TOP 与 TOP-DOWN 融合，才能既知道”哪里脆弱”，又知道”现实里它会被怎么打”——从而把压力精确施加到最该打的地方。**

### 3.3 范式三：静态字典 ──→ 自适应进化引擎（2026/08/27 新增，实证驱动）

> **A/B/C 两度量统计显著证伪**催生本范式。静态操作数字典（全0/全1/交替/subnormal/NaN，含 CSP 配对定向）在 gem5 bit-flip 注入下 diverge 率 A=3.9%/C=3.7%，**统计显著地劣于随机 B=8.0%**（C/B=0.46×, p=0.0083）；结构故障（byte_lane_skew）下 A=2.0%/C=2.8% vs B=8.4%（C/B=0.33×, p=0.0001）。两度量都证伪——**逻辑掩蔽效应在模型级稳健**：静态字典的极端操作数产生确定性结构化结果（0xFFFF+1=0, 0x5555^0xAAAA=全1），bit-flip/byte_lane_skew 命中后被逻辑/CRC 掩蔽；随机操作数无结构冗余，更易 observable diverge。

**范式三的核心洞察**：操作数定向不能用写死的魔术数字（Magic Numbers）或固定模式——那违背了覆盖率引导与动态变异的初衷。必须构建基于微架构反馈信号的**自适应进化引擎**（Evolutionary Engine），从任意普通指令开始，通过算法自动”变异”出具备高 SDC 激发概率的操作数。

**适应度函数**（进化引擎的”指南针”）：

$$Score = W_1 \times T(di/dt) + W_2 \times M(Path) + W_3 \times E(AntiMasking)$$

- **T(di/dt) 动态压力因子**：提取 Unicorn 的 reg_toggle_zero_one/one_zero，计算相邻指令间 bit 翻转总量。引擎不关心操作数是 0x55 还是 0xFF，只认翻转量——翻转量上升则保留变异（梯度上升）。
- **M(Path) 微架构深度因子**：监控执行周期（cycle 代理）或特定微码分支命中率。变异后 cycle 变长（进入慢路径/复杂状态机）则加分。
- **E(AntiMasking) 反掩蔽高熵因子**：检查执行结果的汉明重量与位间香农熵。全 0/全 1/高度周期性（0xAAAA...）得分为负。**雪崩测试**：引入 1 bit 扰动对比两次输出，差异 bit 数越多（雪崩越强）得分越高——**这直击掩蔽问题**。

**三个变异算子**（无固定模式，算法生成）：
1. **Toggle-Driven 梯度爬山**（解决 di/dt 压力激发）：随机反转操作数 bit，跑 Unicorn，若 T 上升则接受并继续，否则回退。几十轮迭代自动逼近物理翻转极限，最终数字毫无规律但产生最大电气瞬变。
2. **边界与差异放大**（解决时序裕量激发）：操作数 ±1/位移，对比变异前后微架构状态差异。微小输入变化导致大状态差异（多触发 op_reg_toggle feature）= 触碰”突变点”（进位链断裂/符号扩展边界），加入精英池。
3. **上下文污染与重组（Crossover）**（解决业务负载高压）：从业务集群抓取高频指令序列插入当前序列前后，前置高功耗指令制造 Voltage Droop，紧接演化出的高 di/dt 指令。

**端到端 pipeline**：Seed（真实业务代码+天然操作数）→ Evaluate（基线 Unicorn 跑）→ Fuzzing Loop（Mutate 100 子代/Simulate/Score&Select 保留 5/AntiMasking 雪崩淘汰）→ Emit SDC Testcase（Score 超阈值且过反掩蔽）→ 上硅测试。

**实测验证**（原型 `tools/sdc_mutator/evolution_engine.py`）：从 ADDS X0,X1,X2 + 普通操作数(0x123/0x456)，三算子演化 **T 8→70（8.8× 提升）**，演化操作数无规律但翻转量最大，E=0.999 高熵反掩蔽。**验证了”算法自动逼近物理翻转极限”的核心机制**。

**Unicorn 覆盖率信号支持**：ArchFeatureGenerator 的 reg_toggle 用 EmitSetBitFeatures+ForEachSetBit **per-bit 粒度**发射，BeforeExecution/AfterInstruction 有寄存器值——T(di/dt)=popcount 可直接计算，覆盖率信号完整支持适应度函数。

**关键待验证**：进化引擎生成的语料 D 是否在 bit-flip + 结构故障两度量击败随机 B（A/B/C/D 四组对比）。预注册 D≥2×B=显著。**未测出 D>B 前不谎称击败 SiliFuzz**。详见实现计划 `docs/superpowers/plans/2026-08-27-sdc-evolutionary-engine-paper.md`。

## 四、三维 SDC 压测空间 (The 3D Stress Space)

为了真正激发 Transient（瞬态）错误，我们构建以下“三维压测空间”技术版图：

1. **微架构与电路脆弱性维度 (Bottom-Up)**
   - 深入分析底层，针对缺乏 ECC/Parity 保护的逻辑、高扇出网络、易发生时序违例的深层流水线进行定向打击。对应 weak 因素 ①②。
2. **执行上下文与指令空间维度 (Core)**
   - 通过操作数的极端变异、指令乱序重排、复杂数据依赖，最大化电路翻转率（Toggle Rate），局部制造极端的 `di/dt`（瞬态电流导致电压跌落），逼出边缘失效。
3. **业务负载特征维度 (Top-Down)**
   - 抽象真实的业务场景模型：数据库重击 LSU/L2C，虚拟化重击 MMU/CSU，HPC 重击 FSU/IEX。对应 weak 因素 ③。

## 五、针对薄弱环节的专项优化设计

### 1. MMU (20% → 突破 TLB/PTW 盲区)
**薄弱原因**：大量电路集中在 TLB（CAM 结构）和 PTW（页表遍历状态机）。常规测试 TLB 命中率极高，无法触发复杂逻辑。
**设计思路（虚拟化/容器负载模拟）**：
- **TLB Thrashing（颠簸）压测**：构造跨大量物理页的随机访问，强制 TLB Miss，高频激活 PTW 硬件状态机。
- **混合页面大小测试**：交替使用 4KB, 2MB, 1GB 映射，压测异构 Entry 匹配与替换逻辑。
- **跨 VMID/ASID 切换**：高频修改 `TTBR0/1_EL1`，瞬间注入访存指令，测试边界隔离与 Flush 逻辑。
- **权限与属性变异**：故意对只读页写、对 Non-cacheable 空间执行原子操作，遍历权限检查的 Gate 组合。
- **业务画像**：虚拟化/容器场景（CSU/MMU 高压）——高频上下文切换 + 跨 VMID 隔离。

### 2. L2C (40%) & LSU (54%)
**薄弱原因**：未能触发 Store Buffer 前递网络、Load Queue 歧义逻辑及 MESI/MOESI 状态转换。
**设计思路（数据库/内存计算负载模拟）**：
- **跨 Cache Line 不对齐访问**：构造跨 64B/128B 边界的 Vector Load，强制触发 LSU 分拆逻辑与状态合并。
- **别名与乱序前递压力**：写宽数据（64-bit）紧接读窄数据（8-bit），压测 Store Buffer 字节拼接脆弱点。
- **伪共享（False Sharing）压测**：多核分别高频读写同一 Cache Line 的不同部分，在 L2 制造 Snoop/Invalidate 流量风暴。
- **缓存驱逐风暴（Eviction Storm）**：基于 Cache Set/Way 参数计算特定步长，强制 L2C 持续发生冲突与 Write-back。
- **业务画像**：数据库/内存计算场景（LSU/L2C 高压）——大量跨行访存 + 伪共享 + 原子自旋。

### 3. OoO 乱序执行 (56%)
**薄弱原因**：均匀指令流无法填满 ROB、Issue Queue 和重命名表。
**设计思路**：
- **长依赖链与管线气泡积压**：用必定 L3 Miss 的 Load 指令打头，后续塞满几十条数据依赖（RAW/WAW）指令。在 Miss 返回瞬间，所有指令并发唤醒，制造极高 `di/dt`。
- **分支预测欺骗与全管线冲刷**：训练 BPU 预测跳转，最后时刻篡改条件使其不跳转，诱导大量幽灵指令执行后引发 Pipeline Flush，压榨乱序恢复/PRF 回滚逻辑。

### 4. IEX (70%) & FSU (80%)
**薄弱原因**：防下限不够，缺乏极致的操作数压力。
**设计思路（操作数空间深度变异）**：
- **操作数翻转率最大化（Max Toggle Rate）**：交替喂入 `0x0000...` / `0xFFFF...` 或 `0x5555...` / `0xAAAA...`，使得 ALU 晶体管 100% 翻转，激发老化（HCI/NBTI）引发的时序违例。对应 weak 因素 ②。
- **进位链极限测试**：构造 `0xFFFFFFFF... + 1`，强迫进位信号穿透最长组合逻辑路径——降频或老化芯片上最易高位算错。
- **FSU 特殊操作数攻击**：大量注入 Subnormal（非规格化数）、NaN、Infinity，强制 FSU 进入微码或慢路径等极度脆弱的逻辑盲区。
- **业务画像**：HPC/AI 推理场景（FSU/IEX 高压）——持续满载 FMA + 极端浮点操作数。

| 跨 cache line / 前递压力 | LSU | V4: LSU 跨边界访存 | 2 AGU, cross-16B +1-2cyc, StFwd 6-7cyc |
| 一致性状态机竞态 | L2C / MMU | V5: 跨 NUMA 一致性 | 4-node distance 10-24, HCCS, HHA |
| 独立供电域启停时序 | FSU / IEX | V6: 密码硬核启停 | AES/SHA/CRC32 独立单元 |

## 七、技术版图与持续布局（前瞻）

> 可以把 SDC 的压测整理出来几条技术版图，后续持续布局，真正打开核心点。这些方向大多是探索性、护城河型工作。

**五条可长期布局的技术线：**

1. **微架构脆弱性测绘（Bottom-Up 测绘）**
   - 从设计端打开，结合布线布局与电路覆盖率，找出最脆弱的模块/功能/网络（无冗余、高扇出、长组合路径、易时序违例）。当前无现成自动化工具，需探索。

2. **操作数空间变异引擎**
   - 废弃纯随机数生成器，建立“全 0/全 1/交替位/Subnormal/NaN/极大极小值”硬核种子字典，对每条指令做操作数维度的深度变异，把覆盖率空间从“指令种类”扩展到“操作数组合”。

3. **动态压力放大器（环境毒化）**
   - 用功耗病毒、带宽风暴、跨 NUMA 流量在目标单元上叠加 di/dt 与时序压力，把潜伏的 transient 逼出来。是 SDC 检出的“放大器”。

4. **业务负载画像与权重分配**
   - 抽象数据库（LSU/L2C）、虚拟化（CSU/MMU）、HPC（FSU/IEX）的访存与计算模型，按部署场景给上述技术线分配权重。

5. **演化反馈闭环**
   - 真机检出的 SDC 触发用例回灌为种子，局部变异放大，形成“压测 → 检出 → 回灌 → 再压测”的闭环（详见 plan 文档第四部分）。

**工程现实**：学术界对真实系统架构一般缺乏理解，但擅长先进算法研究，算法研究与工程实操两条腿走路——既要有微架构级脆弱性建模的前瞻研究，也要有汇编种子落地、编译器控制、真机验证的工程硬功夫。

## 八、落地规划：构建动态用例生成器流水线

为了将上述理论转化为工程实操，避免单纯纸上谈兵，后续实施将遵循以下流水线（可执行细节见 `kunpeng920_sdc_plan.md`）：

1. **定义操作数变异字典**：废弃纯随机数，建立包含“全 0、全 1、交替 0/1、Subnormal、NaN、极大/小值”的硬核种子库。
2. **构建微架构场景模板（Micro-arch Templates）**：
   - *Template 1 (LSU/OoO)*: Load Miss → 依赖链积压 → 唤醒风暴
   - *Template 2 (MMU)*: 跨页表配置 → TLB Miss → 异常捕获
   - *Template 3 (L2C)*: 多核缓存行冲突 → LSE 原子指令自旋
3. **组合与编译器控制**：利用 LLVM/GCC 内联汇编，彻底禁用编译器自动优化（防止死代码消除），强制生成上述特定的指令拓扑。
4. **业务模型权重分配**：根据目标服务器画像（如数据库、HPC），在生成的最终语料库中动态分配上述 Template 的比例。
5. **演化反馈闭环**：真机检出 SDC → 回灌种子 → 局部变异放大 → 再压测（见 plan 文档第四部分“演化反馈闭环”）。
